# 订单接入与自动提交流程

> 代码依据：`mq/OrderSendListener`、`handler/order/resolve/AbstractOrderHandle`、`OrderServiceImpl.saveOrUpdateOrder/saveOrder/update`、`job/OrderJobHandler.autoSubmitJob`。

## 一、订单来源与入口

1. **线上订单（平台同步）**：openapi 服务从各平台采集订单存入 Mongo，发 MQ 消息（`SendOrderMqDto`：platformId + mongo 记录 id）。SMS 的 `orderSendInput` 消费者按 platformId 加载对应 `OrderHandle`，调 `consumeOrder`：
   - 先 `queryOrderFromMongo` 取该条订单的完整结构化数据；
   - 再 `resolveOrder` 解析入库。
   - 消费失败会抛出异常（依赖 MQ 重试）。
2. **主动拉取补偿**：`pullOrderFromMongo` 按条件批量从 Mongo 拉取未同步订单，走同一套 `resolveOrder`（非 MQ 来源，失败只记日志不抛出）。
3. **线下订单**：界面手工新增（`add`）或导入，`orderOpType=NONE`；手工创建的 C 端线下单停留在草稿+step=INIT，需要人工 `submit` 提交。
4. **鲸汇（JingHui）订单**：走平台 99 的解析器，属于"代发/ERP 对接"特殊链路（见边界条件）。

## 二、解析入库（resolveOrder）

逐条处理，流程：

1. **平台过滤**：
   - 鲸汇（99）：只解析状态为 `FH`（发货）、`QX`（取消）的订单；来自 Amazon 且非自发（fulfillment_channel != 2）的不解析。
   - Amazon（1）：MFN 自发单不解析（Amazon 自发走其它来源）。
2. **解析**：`apiResolve` 把平台结构转成 `OrderSaveDto`（主单+明细+地址+费用），返回 false 表示该条跳过，并回写同步完成标记。
3. **校验（checkOrder）**：原单号（orderSnSource）、shopId、insertMongoTime（Mongo 版本号）三者缺一不可，否则抛异常。
4. **入库**：`orderService.saveOrUpdateOrder(orderSaveDto)`。
5. **回写同步标记**：`updateSync` 通知 openapi 该订单已处理（按 platformId+shopId+原单号+insertTime 定位）。

## 三、新单保存（saveOrder）

入口加 Redis 锁：`ORDER_PULL_LOCK_KEY + shopId + sourceCode`，防止同店铺同原单号并发入库。

**初始状态判定**（非鲸汇单）：
- 平台状态=已取消 → 直接 **已取消**；
- RMA 重发单 → **待审核**；
- 代发单（ISS_SEND）且已带状态 → 按给定状态；
- 其它 → **草稿**。

**步骤（step）判定**：
- 鲸汇单 → step=FINISH（不参与自动提交）；
- 非鲸汇：默认 step=INIT；若该订单满足自动提交条件（`orderSaveDto.autoSubmit()`）：
  - 代发单 → step=SUBMIT（跳过混仓拆单与自动分仓）；
  - 直发/混仓 → step=MIXED_SPLIT（进入自动拆单分仓流水线）。

**单号**：通过序列号服务生成，前缀 `SALES_ORDER_PRE`（SO 单），6 位序号；若原单号为空则 orderSnSource=orderCode；sourceCode 默认取 orderSnSource。

**随主单落库**：OrderCost（先按平台规则计算营销收入 marketIncome）、OrderAddress、OrderItem、OrderItemSon（系统 SKU 明细）、OrderItemCost。

**鲸汇特例**：
- 保存时若为已发货状态：立即把关联发货通知单置为已发货并回写运单号，同时调 WMS `addOutbound` 走出库流水（失败记入 `OrderResolveFailRecord`，类型 OutboundFail）；
- 鲸汇待发货单保存时先尝试 `occupyInventory` 占用库存（失败记 OccupyStockFail）。

## 四、旧单更新（update）

同一原单号已存在时进入更新分支。按订单 id 加 `ORDER_LOCK_KEY` 锁逐条处理。

### 4.1 忽略更新（边界）——忽略则整条跳过
- 本次推送不是完整态（finishFlag=false）→ 忽略；
- 本次版本（insertMongoTime）早于库中版本 → 忽略（防乱序）；
- 终态保护：
  - Shopee/Amazon：已取消、已完成 后忽略；
  - 其它平台：已发货、已取消、已完成 后忽略（`ignoreUpdate`）；
- 线上单但已被人工修改过（变成人工单）→ 忽略（不再被平台数据覆盖）。

### 4.2 自动提交冲突保护
旧单是草稿且 step != INIT（正在自动提交流水线中）时收到更新 → **抛异常**，依赖 MQ 重试或人工处理（避免拆单分仓与改单并发）。

### 4.3 变更判定（judgeOrderChange）
依次比较：地址、主单基础字段、SKU 明细、SKU 费用、订单费用；任一有变化记入变更日志并标记 change。
- 有变化且平台状态无售后/取消情形 → 截单类型记为 **API_UPDATE**（平台信息更新）。

### 4.4 平台状态引发的截单（calCutType）
解析器把平台最新状态映射成截单类型：退款中/退款完成/部分退款/未付款取消等。处理分支：
- **旧单=待发货**：先走截单（含 WMS 拦截）：
  - 拦截失败（REJECT）→ 不更新订单信息；
  - 拦截成功/拦截中 → 继续 `orderChange` 更新信息。
- **旧单=已发货**：只做有限的发货后更新（`deliveryOrderChange`）：Shopee 仅更新其它收入，Amazon 仅更新店铺优惠（couponFee），并更新版本号。
- **其它状态（草稿/待审核/问题件）**：先截单（转问题件或取消），再更新信息。

### 4.5 orderChange 的内容
- 记录变更日志；更新主单（状态、支付时间、标签、代发单的运单/快递/发货时间）；更新地址、费用。
- **SKU 变更**（数量或 sellerSku 变化）：
  1. 若订单处于锁定中 → 先 `unlock(id, false)` 释放占用（保留 lockTime）；
  2. 删除旧 OrderItem/OrderItemSon，写入新明细；
  3. 只要曾经有 lockTime → 重新 `lock`（重新排队占库存）。
- 更新明细费用（按 sellerSku 分组重配）。

## 五、自动提交（autoSubmitJob）

定时任务，先抢全局锁 `ORDER_SUBMIT_LOCK_KEY`（上次未跑完则跳过本次）。

`autoSubmit()`：扫描草稿单中 step ∈ {MIXED_SPLIT, AUTO_WH, SUBMIT} 的订单，逐个 `autoSubmit(orderId)`：

1. 加 `ORDER_LOCK_KEY+orderId` 锁（tryLock 失败跳过）；
2. 状态必须=草稿、step 必须在自动码内，否则跳过；
3. 按 step 执行一步（每次任务只推进一步，下次任务继续）：
   - **MIXED_SPLIT（混仓拆单）**：直发单/代发单直接改 step=AUTO_WH；混仓单调 `warehouseSplitStrategy.split` 拆成自发子单（step=AUTO_WH）与代发子单（step=SUBMIT，仓库取店铺默认仓）；
   - **AUTO_WH（自动分仓）**：调 `autoWhRuleService.autoWh` 按自动分仓规则匹配仓库+快递方式（未匹配到只记"自动分仓失败"日志，不阻塞），step→SUBMIT；
   - **SUBMIT（提交完成 orderAutoEnd）**：
     - 平台状态已取消 → 直接取消（"同步平台订单状态更新为已取消"）；
     - 草稿 → 置为 **待审核**，记提交日志；
     - 移除"订单提交中"标签；
     - 代发单：加"平台仓发货"标签；若平台仓状态已发货/已完成 → 订单直接置 **已发货**；
     - step→FINISH；
     - 最后统一 `autoSplitAndAllocateWarehouse`（兜底：对需要拆单/分仓的单再执行一次自动拆单+分仓，RMA 属性单除外）。

### 边界条件汇总（自动提交）
- 只有草稿单参与；每个 step 幂等、可中断续跑；
- 订单被锁（并发编辑/截单）时当轮跳过，不报错；
- 混仓拆分后原单被取消（拆单取消标签），子单继承费用按数量分摊，最后一个子单用减法兜底精度；
- 代发单跳过自动分仓，仓库=店铺绑定仓。

## 六、人工提交（submit）

仅允许 **C 端线下手工单**（isManuallyAddSaleOrder）：
- 前置：状态必须是草稿；加订单锁（占用则报"全局锁被占用，请稍后再试"）；
- 提交后：step=FINISH、状态=待审核，随后立即执行一次自动拆单+自动分仓（`autoSplitAndAllocateWarehouse`）。

## 七、问题件转待审核（toAudit）

- 仅问题件可转；加订单锁；
- 状态改为待审核并记日志"问题件转待审核"；同步刷新 RMA 重发单状态。
